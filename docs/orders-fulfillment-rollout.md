# АвтоСклад63 — сквозной контур заказов и движения готовых чехлов

Дата: 2026-11-25. Статус: проектирование, READ-ONLY; никакие заказы, резервы и отгрузки в МойСклад ещё не создаются.

## Цель
Единая цепочка: канал продаж → заказ → потребность в пошиве/наличие → готовый товар → подбор → упаковка/маркировка → физическая передача → отгрузка в МойСклад → возврат/отмена. Финансы отдельно: поступление денег ≠ дата отгрузки, комиссия маркетплейса ≠ физическое списание.

Каналы: Ozon, WB, Яндекс Маркет, Авито, торговая точка Пламя, дилеры Руслан и Ирина. У каждого заказа — обязательные account/legalEntity, channel, sellerCabinet, marketplaceMode (FBS/FBO/аналог или local), externalOrderId, shipmentId, ordered SKU, variant, quantity, date, shipDeadline, destination, workflowState. Для ручных каналов — собственный уникальный номер и документ-основание. Не полагаться на текст названия модели для сопоставления SKU.

## Минимальные состояния
IMPORTED → MAPPED → STOCK_ALLOCATED / PRODUCTION_REQUIRED → PRODUCTION_ASSIGNED → READY_FOR_PICK → PICKED → PACKED → LABELLED → HANDED_OFF → DISPATCH_CONFIRMED.
Отдельные ветки: CANCELED_BEFORE_HANDOFF, RETURN_IN_TRANSIT, RETURN_RECEIVED, RETURN_QC_ACCEPTED / RETURN_REJECTED, EXCEPTION. Фактическая передача, подтверждение площадки и получение оплаты — три разных события.

## Разделение ответственности
- Ольга: вечером видит автоимпорт заказов по всем подключённым кабинетам, подтверждает только исключения, формирует очередь завтрашних заказов/маркировки; не набивает вручную полученные по API заказы.
- Старшая швея: принимает дефицит по SKU, назначает задания и сроки, фиксирует завершение/передачу; не создаёт второе производственное задание на уже выпущенный комплект.
- Швеи: отмечают выпуск по конкретному заданию и SKU; сообщения MAX — резервный канал сообщения, не второй источник оформления производства.
- Илья: контролирует расхождения productiontask ↔ готовый товар, сопоставление SKU и документы-исключения, а не переписывает ежедневный чат вручную.
- Ирина (упаковка): сверяет лист подбора, физический комплект, ярлык/заказ/маркировку, фиксирует PACKED и факт передачи водителю/перевозчику.
- Дмитрий: подтверждает физическую передачу на отправку по листу/партии; для Пламени и дилеров отдельная фиксация выдачи/доставки.

## Документооборот МойСклад
- Заказ покупателя (customerorder) — заявка/резерв в рамках выбранной политики; резерв сам по себе НЕ уменьшает физический остаток.
- Выпуск в производстве — уже существующие задания и этапы; не создавать дополнительное поступление готовых чехлов.
- Отгрузка (demand) — по подтверждённой передаче с правильного склада и юридического лица; не оформлять вторую отгрузку, если интеграция маркетплейса создала её.
- Перемещение (move) — когда готовая продукция переводится между цехом, Пламенем, внешними/дилерскими складами; передача на реализацию и FBO требует отдельного договорного сценария, не подменять обычной продажей.
- Возврат покупателя — только после подтверждённого поступления и ОТК, с возможностью непригодного возврата без свободного остатка.
- Для точки и дилеров: различить продажу с немедленной оплатой, отгрузку с отсрочкой и передачу на реализацию; конкретный документ выбирается после подтверждения договорной схемы.

## Защита от двойного списания
Одна учётная операция на ключ (legalEntity,channel,sellerCabinet,externalOrderId,shipmentId,operationType,SKU,quantityVersion). Хранить external order/shipment id, MS document id, document update/version, status, firstSeenAt, lastSeenAt, source. D1 должна обеспечивать UNIQUE; повторный импорт делает UPSERT без второго документа. Документы МойСклад сначала искать по внешней метке/связи; дубликаты ставить в CONFLICT, не автоисправлять.

Один и тот же FBS/FBO заказ не импортировать сразу через штатную интеграцию и самописный writer. Существующие интеграции Ozon/WB/Яндекс нужно сначала инвентаризировать. Отличать ФБО-поставку от конечной продажи, резерв, физическую передачу и расчёт выручки.

## Контрольные правила
1. Перед отгрузкой проверить соответствие legalEntity, warehouse, SKU, variant, qty, соответствующий выпуск/наличие, уникальный внешний ID, отсутствие ранее проведённой отгрузки.
2. Отмена до отгрузки снимает только резерв; после передачи — возвратный процесс, не удаление документов.
3. Никогда не проводить массовые отгрузки исторических заказов без проверки повторов и исходных документов.
4. Отрицательный остаток или неподтверждённая единица → исключение, а не оприходование «для закрытия».
5. Не отправлять полный адрес/телефон покупателя в чат MAX или журналы ошибок.
6. Финансовый Ozon/WB/Яндекс модуль не пересчитывать по факту создания customerorder/demand. Только согласованные связки для аналитики.

## Очередность внедрения
Этап A (без записи): аудит текущих интеграций и юридических лиц, FBS/FBO, всех кабинетов, сопоставления SKU и складов, каналов ручной продажи; read-only импортер и панель 'Заказы' с дедупликацией/исключениями. Критерий: входящие заказы всех доступных по API каналов читаются без ручного ввода, UNKNOWN отдельно.
Этап B (пилот записи): только один подтверждённый канал и один склад, новые заказы, 5–10 реальных операций, без бэкфилла/массового проведения. Подтверждение отгрузки человеком и сравнение МойСклад с фактической передачей. Откат — остановить writer, не удалять документы задним числом.
Этап C: расширить каналами, ручной ввод для Авито/точки/дилеров, сканирование/пакеты, возвраты, сверка ежедневно 'получено → выпущено → передано → отгружено'. После пилота отдельно согласовать полную автоматическую проводку.

## KPI
Заказы без соответствующего MS документа; дубли по внешнему номеру; заказ без SKU; отгружено без факта передачи; передано без отгрузки; отменено с висящим резервом; просроченные к пошиву; комплекты на наличии по складам; возвраты без ОТК. Источник KPI и время последней синхронизации обязательны.

## Принятые ограничения
Физический пересчёт материалов отложен; эти минусы не исправляются в рамках проекта заказов. Прежде чем включить запись — подтвердить права токена, привязку SKU и схему FBS/FBO/склад/юрлицо по каждому кабинету, а также поведение штатных интеграций. Не изменять рабочие финансы и схему производства без выявленной ошибки.
