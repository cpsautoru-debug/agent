# Рабочая панель производства и склада — АвтоСклад63

Этап дорожной карты CTO: достоверный учёт до ИИ-диспетчера.

## Что увидит руководитель

В разделе «Контроль производства» действующего тестового офиса:
- четыре обзорных показателя: производственные задания **в реестре всех лет**, результат проверки **только видимой страницы**, количество позиций/складов **только в текущем складском отчёте**, статус подключения отдельной готовой продукции;
- рабочие поиск заданий, этапы и ручной аудит;
- складской отчёт с названиями номенклатуры, складов, физическим остатком, резервом и ожиданием;
- поиск по названию и страницы по 10 позиций без автоскана;
- отрицательные остатки выделены явно, неизвестные количества не превращены в ноль.

Это **не** полная текущая незавершёнка, не полный баланс, не подтверждённый дефицит и не автоматизированное списание. Готовую продукцию не смешиваем с этапом «Готово к отгрузке».

## Откуда берём реальные остатки

Ручное чтение одной страницы /api/remap/1.2/report/stock/bystore?limit=10&offset=N (с безопасным фильтром search по запросу). Отчёт содержит ссылки на номенклатуру, но **не названия товаров**. Для отображения названий выполняется **один дополнительный** ограниченный GET /entity/assortment?limit=10&filter=id=UUID1;id=UUID2... по идентификаторам той же страницы. Нельзя сопоставлять эти два списка по порядку строк — только по проверенному UUID. Если название не найдено, показывается «Наименование не передано», не придумывается название. stockByStore содержит реальные имена складов. Не закрепляем число или названия складов в исходниках.

Маршрут офиса /api/ms/stock-bystore: owner-only сессия Google + проверка владельца в D1; токен МойСклад остаётся на сервере; строго GET и не более двух последовательных ограниченных внешних запросов; без записи, автоповтора, Cron или массовой загрузки. Ограничение 256 КиБ ответа, тайм-аут 25 секунд.

Отчётные поля: stock — физическое количество; reserve — резерв; inTransit — ожидание. **Не суммировать** и не выдавать отсутствие поля/склада за ноль. Число позиций отчёта не равно количеству метров кожи или комплектов чехлов. При отказе API данные отмечаются как неактуальные, без придумывания остатков.

## Задания с разными технологическими цепочками

Пилот показал, что задание №00740 содержит разные производственные позиции (пошив ковров и другие этапы): общий план был 2 единицы, а каждый шаг одной позиции — 1 единица. Старый код проверки сравнивал план отдельного шага с общим планом задания и оставлял ошибочное «Не подтверждено». Теперь API проверяет последовательность выполненных количеств **по каждой производственной позиции**, а не по одной агрегированной цепочке. Несогласованную цепочку оставляет непроверенной. Выполнение учтённых этапов не означает отгрузку или закрытие заказа.

## Что необходимо проверить после публикации

1. Все CI-тесты по производству и складу зелёные; протестированы авторизация, негативные остатки, пустые поля, лимит страницы, смешанные цепочки.
2. Cloudflare раздаёт новые JS-модули; без авторизации API остатков и заданий возвращает 401 JSON.
3. Владелец вручную нажимает «Обновить остатки» один раз, чтобы проверить реальный ответ. Если отчёт или запрос названий вернёт ошибку — разбираем безопасный код, не выдумываем остатки.
4. Сверяем несколько реальных позиций в основном и внешнем складах через интерфейс МойСклад. Лишь после сверки норм, перемещений и фактических остатков готовим контроль дефицита.
5. Для производства повторно проверяем №00740 и ещё 1–2 задания. Полный проход 744 записей не включать, пока не доказаны надёжность, лимиты, паузы и полнота результата.

Дальше по утверждённому 90-дневному плану: достоверная производственная очередь, отдельный складской учёт материалов и готовой продукции, затем связка с заказами, KPI и ИИ-диспетчер. Никаких изменений в производственных документах, остатках, финансах, секретах или Cron.
