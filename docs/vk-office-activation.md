# ВК: управляемое подключение онлайн-офиса

Ответственный: инженер интеграций; владелец проверяет доступ и согласует запуск сервера.
Вход: подтверждённая FAQ-база, сообщество autosklad63, ключ сообщества в Render, закрытый Sites.
Результат: новые личные сообщения и журнал публикаций в защищённом офисе.
Готовность: реальная проверка прав, сохранение журнала, ручной тест владельца без дублей.

## Разделение доступа

- Render хранит `VK_COMMUNITY_TOKEN`; браузер не получает ключей ВК.
- Новый `/vk/office` принимает только POST с отдельным `VK_OFFICE_BRIDGE_KEY` (случайный секрет минимум 32 символа). Разрешены фиксированные действия status/reply/publish, не произвольный API.
- `VK_PUBLISH_TOKEN` — отдельный пользовательский ключ для wall.post. Ключ сообщества не заменяет его. Вводить только в Environment Render, не в чат.
- `VK_OFFICE_SERVICE_TOKEN` — существующий служебный доступ именно к закрытому офису. Передаётся только в заголовке OAI-Sites-Authorization.
- Sites получает тот же bridge key, `VK_GROUP_ID`, `VK_AUTO_REPLIES=false` до проверки. Пользовательские запросы проходят закрытый доступ Sites и проверку Origin; callback требует отдельный bridge key.
- D1 (`DB`) содержит сообщения, действия, состояния и блокировки, R2 (`BUCKET`) — только явно сохранённые владельцем макеты. Переписки не попадают в Git.

## Поведение

Автоответы включаются в панели после проверки прав. Старые события, исходящие, групповые сообщения и события другого сообщества пропускаются. Неизвестный вопрос, вложение, неопределённая отправка или параллельные сообщения передают переписку владельцу и останавливают её автоответы. Это FAQ, а не подключённая языковая модель.

Запись сообщения и уникального ID выполняется до отправки. Блокировка одного собеседника постоянная: сбой не разблокирует её автоматически. После ручного разбора восстановление требует отдельного технического действия. Это сознательный безопасный режим первого запуска.

Студия готовит макет и текст; владелец подтверждает условия и права. Сохранение создаёт проверенный черновик в D1. Отдельная кнопка публикации делает атомарный переход approved → processing → published. При неопределённом результате — unknown, повтор запрещён до проверки в ВК. Расписаний и фоновых публикаций нет.

## Проверка и запуск

1. Запустить существующие тесты, vk-office.test.mjs и worker.test.mjs. Все API заменены тестовыми ответами.
2. Проверить diff отдельного PR. Объединение и Render Deploy — только по отдельному разрешению владельца.
3. Сохранить ID текущего успешного Render deploy и версию Sites для отката; сохранить текущую конфигурацию без вывода значений.
4. Развернуть проверенный commit сервера. Добавить только перечисленные новые переменные, не менять MAX/Bridge/МойСклад.
5. Опубликовать owner-private Sites с D1/R2, применить схему `apps/vk-office/schema.sql` через schema-only migration.
6. В защищённой панели проверить точное сообщество и отдельные права messages/posts/stories. Наличие ключа не равно успешной проверке.
7. Включить ответы кнопкой панели. Владелец отправляет новый вопрос по FAQ, проверяет ответ и один элемент журнала. Затем неизвестный вопрос: автоматической отправки быть не должно; следующий FAQ остаётся у владельца.
8. Подготовить реальный материал, просмотреть текст/фото, публиковать только после согласования конкретного материала. Проверить ссылку и запрет второго клика. Не создавать технический тестовый пост для подписчиков.

Аварийная остановка: выключить ответы в панели; при недоступном офисе убрать только новые relay-переменные Render и развернуть предыдущий успешный commit. Вернуть предыдущую версию Sites. D1-журнал сохранить, не очищать для повторной отправки. При проблемах прав публикующие кнопки остаются недоступны.

Ограничения: Render Free засыпает, поэтому старт может задержаться. В журнале отображаются последние 50 действий; автоматическая очистка/экспорт и восстановление заблокированной переписки требуют следующего этапа. Посты требуют отдельного ключа пользователя с правами; возможность сториз проверяется ВК для данного сообщества.
