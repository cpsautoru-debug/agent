# АвтоСклад63 — пульт руководителя производства

Дата: 20 ноября 2026. Тестовый онлайн-офис: \`/#production\`. Реализация без Codex.

## Цель

Убрать из ежедневной работы необходимость вручную открывать десять отдельных заданий только ради ответа «на каком этапе сейчас заказ». Использовать существующие проверенные owner-only API для **небольшой ограниченной оперативной выборки**. Это интерфейс наблюдения, а не система списаний или выдачи поручений.

### Реальные источники

1. \`GET /api/ms/production-feed\` — первые 5 документов по дате создания/документа (не статусу актуальности). Далее при наличии \`hasMore\`: \`?offset=5\`. В отчёте \`totalAllTime\` содержит **все** исторические документы (из ранее проверенного реестра было 744), это **не** число активных заказов.
2. \`GET /api/ms/production-stages?taskId=<UUID>\` — проверка **ровно одного задания**, с учётом отдельных цепочек разных позиций. Библиотека \`assessProductionTask\` определяет статусы: \`incomplete\`, \`complete\`, \`unverified\`. Не подтверждённое не превращаем в завершённое, а проведение задания не означает отгрузку.
3. \`classifyProductionPlanDate\` проверяет **календарную** дату по Самаре **только** для подтверждённо незавершённых; это не договорный SLA.
4. Однокнопочный складской \`GET /api/ms/warehouse-snapshot\` остаётся отдельным действием. После подтверждённой загрузки его публичный интерфейс передаёт **только агрегаты текущего склада** через браузерное событие \`ms:warehouse-snapshot-ready\`. Новых HTTP-запросов для верхней сводки нет.

### Пределы нагрузки

- Сканирование только по кнопке владельца «Проверить последние 10».
- Не более **12 последовательных** внутренних owner-only GET (до 2 страниц реестра, до 10 этапов заданий), пауза **2 секунды** между запросами. Нет параллельного fanout/автоповторов/записей.
- При смене вкладки, закрытии производственного раздела, нажатии «Остановить» **новые** запросы не начинаются после завершения текущего шага. 429, 401, 403, 503 прерывают процедуру. Непроверенные отдельные этапы отображаются только как \`unverified\`.
- При конфликте количества исторических документов между страницами, дублировании номеров/UUID, неправильном формате API — статус \`ms_production_board_unverified\`. Частичная таблица не показывается как подтверждённый результат.
- Данные держатся в памяти вкладки, не передаются маркетплейсам и не пишутся в D1. Импорты/изменения \`МойСклад\` запрещены.

## Что делает руководитель

1. Открывает \`Производство и склад\`.
2. Нажимает **«Проверить последние 10»**. Получает статистику **только этих десяти последних** документов и таблицу: номер, подтверждённый статус, оставшееся количество (условные единицы исходных позиций), первый незавершённый этап, плановая дата и ориентировочный признак её прохождения.
3. Нажимает «Открыть №...» — номер переходит в существующий **точный поиск**, можно посмотреть этапы одного заказа.
4. Для материала/товаров нажимает «К обзору складов» и запускает один складской срез отдельно. Группа и статус не подменяются товаром по названию.
5. При ошибке текущих этапов показывает «Не подтверждено»; при 429/неверной структуре — остановка без выдуманных KPI.

## Подтверждённая проблема качества номенклатуры

Владелец предоставил скриншот \`Пламя. Магазин\`:
- **31** позиция с ненулевым учётным остатком;
- **16** позиций относятся к подтверждённой группе \`Коврики Ева Пресс форма/Иномарки/... \`;
- **15** оставшихся (судя по видимым названиям, EVA-коврики) имеют статус «Группа не указана» и единицу «Не указана». Считать их категорией EVA **в управленческой сводке автоматически нельзя**; необходимо поправить карточки после проверки.
- Это не обоснование классификации готовых **авточехлов**; их фактические группы в каталоге не подтверждены.

## Честная граница этапа

**Выполнено**: защищённое чтение задания и этапов, ручной аудит до пяти, оперативный пульт до десяти последних, поиск задания по номеру, наличие выбранного склада до сорока ненулевых SKU, категории только по фактическому пути номенклатуры, авторизация владельца, тесты безопасности и Cloudflare staging.

**НЕ выполнено / запрещено считать готовым без источника**:
- Полный актуальный реестр **всех незавершённых** заданий. Исторические 744 документа не равны работе сегодняшней смены. У API нет подтверждённого серверного статуса незавершённости; без этого полное чтение потребует сотен отдельных проверок этапов и надёжного графика API.
- Фактическое сопоставление **покупательский заказ → производство → готовая продукция → выдача/отгрузка**.
- ФИО швей/ОТК и сроки **каждого этапа** (не подтверждены связями).
- Объединённый товарный баланс всех четырёх складов (обзор >40 ненулевых SKU намеренно прекращается, нет консистентного общего среза) и полноценная сверка перемещений.
- Расчёт дефицита материалов и количества комплектов (требуются подтверждённые техкарты, единицы расхода, взаимозаменяемость сырья, остаток с учётом резервов, физический пересчёт).
- Автоматические задания, обновление «МойСклад», списания, закупки и ИИ-диспетчер. Нельзя переключать эти возможности на основе неподтверждённых данных.

## Контроль приёмки

1. GitHub CI: проверка каждого из 10 последних документов (12 внутренних запросов, 11 пауз), смешанных и неверных цепочек, просроченного календарного дня только для подтверждённой незавершёнки, 429/cancel/mismatched historical total, запрет ложной полноты.
2. Тестовая Cloudflare: HTML и \`ms-production-command-board.mjs\` HTTP 200 и JS MIME; прежние анонимные API \`/api/ms/production-feed\` и \`/api/ms/warehouse-snapshot\` отвечают HTTP 401 JSON. Никаких изменений секретов/продакшен.
3. Владелец может один раз вручную нажать «Проверить последние 10». Реальная приёмка этих 10 ещё требуется после выпуска, а данные владельца из GitHub/Cloudflare без Google owner-session не доступны.
4. После этого следующий CTO этап — согласовать готовые авточехлы и эталон связей заказов с производством; согласовать безопасную выборку текущих незавершённых без перебора всех исторических заданий. Не переключать автосканы без верификации нагрузки.
