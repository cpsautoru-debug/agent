# MAX: изолированный тест упаковки и отгрузки — Issue #3

Ответственный: владелец. Вход: только вымышленные заказы, четыре вымышленные швеи и роли. Результат: план 15 (Ozon 8, ВБ 3, Авито 2, Пламя 2), произведено 16, упаковано и принято водителем 15, остаток 1. Готовность кода: автоматические проверки; готовность подключения: отдельная ручная проверка после разрешённого запуска.

## Изоляция

По умолчанию выключено. Для отдельного тестового экземпляра нужны `MAX_PACKING_TEST_ENABLED=true` и абсолютный `MAX_PACKING_TEST_DIR` в отдельном закрытом каталоге, например вне репозитория или внутри игнорируемого `private/`. Не использовать общий каталог с рабочими данными. Значения Render этим PR не меняются. Рабочий Apps Script не изменяется и не вызывается тестовыми командами.

Команды только `/test …`, только свежие подписанные события владельца `MAX_OWNER_ID` в личном диалоге. Роли симулируются владельцем, идентификаторы сотрудников не используются. Единственный сетевой вызов тестового обработчика — ответ владельцу в MAX. Google Bridge, МойСклад, зарплата, реальные остатки и отчёты не участвуют. Обычные команды работают прежним путём.

Файл `packing-test-v1.json` содержит отдельное пространство имён, сценарий, хеши ID сообщений, результаты и журнал: UUID операции, время UTC, роль, разрешённое название действия, результат. Произвольный текст сообщений не сохраняется. Состояние заменяется атомарно после fsync; блокировка исключает конкурирующие записи. Повтор сообщения возвращает прежний ответ; повтор операции с новым сообщением отклоняется. Ошибка записи/доставки возвращает HTTP 503, рабочий Bridge не вызывается.

## Ручная проверка владельцем

Не запускать production deployment в рамках этого PR. До отдельного разрешения доступна только локальная проверка: `node --test apps/max-agent/packing-test.test.mjs`. Она использует временные каталоги, подменённые webhook и отправку MAX, без доступа к внешним сервисам.

После отдельного согласования тестового запуска отправлять в личку:

1. `/test` — подсказка и пометка ТЕСТ.
2. `/test role olga`, затем `/test plan` — план и готовность маркировок 15.
3. `/test role alexandra`, затем по очереди `/test produce 1`, `/test produce 2`, `/test produce 3`, `/test produce 4` — 16 изделий.
4. `/test role irina`, `/test pack`, `/test handover` — упаковка 15 и ожидание водителя.
5. `/test role dmitry`, `/test accept`, `/test status` — принято 15, осталось 1, списание 0, приёмка маркетплейсом неизвестна.
6. Повторить `/test accept`, `/test produce 1` — отказ, количества не увеличиваются. Проверить упаковку до производства и под неверной ролью — отказ.
7. Отправить `/test` из другого аккаунта или группы — никаких ответов/изменений. Реальные сотрудники не участвуют.
8. Перезапустить тестовый процесс с тем же каталогом; `/test status` сохраняет результат. Повтор webhook с тем же mid проверяется автотестом, обычная повторная отправка получает новый mid.

## Ограничения и восстановление

Только фиксированный сценарий, не производственный модуль упаковки. Отправка ответа MAX имеет доставку как минимум один раз: после сбоя ответ может повториться, учётное действие не повторяется. Лимит 2000 событий на сценарий; нет автоматического удаления журнала. После аварии оставшиеся `.lock`/`.tmp` требуют проверки оператором при остановленном тестовом экземпляре, автоматического снятия блокировки нет. Повреждённые данные не перезаписываются. Для нового прогона остановить тестовый экземпляр и выбрать новый пустой каталог, предыдущий сохранить для аудита. Эфемерный диск Render не обеспечивает сохранение после развёртывания — для ручной проверки нужен отдельный сохраняемый каталог; никаких настроек инфраструктуры PR не включает.

Не проверялись живой MAX-диалог и реальная доставка: запуск и deployment не разрешены. Критерий прохождения владельцем в MAX подтверждается только после такого отдельного теста.
