# Полный контроль незавершённого производства — план безопасного запуска

Статус: **диагностика в отдельном PR, полный сканер НЕ включён**.
Источник: «МойСклад» JSON API 1.2. Разрешённые операции на данном этапе — только чтение.
Проверки выполняет владелец вручную из раздела «Производство».

## Почему нельзя сразу сканировать все документы

- Документ «проведён» не означает «выполнены все производственные этапы».
- Документ «Производственное задание» поддерживает выборку по номеру/датам, но подтверждённого серверного фильтра именно *по фактической незавершённости всех этапов* нет.
- Контроль только последних 5 заданий пропускает старые незавершённые.
- Производственные этапы учитываются по производственным позициям; промежуточные этапы нельзя складывать с последним и выдавать за готовую продукцию.
- При пропусках, неоднозначной схеме этапов, ошибке API и изменениях во время постраничного чтения полноценный отчёт не доказан.

## Этап 1: два малых запроса API

Ручная кнопка «Оценить объём API» вызывает owner-only
`GET /api/ms/production-coverage-probe` без параметров:

1. Один `GET /entity/productiontask?limit=1&offset=0` — только счётчик всех документов и один образец, образец не выводится пользователю.
2. Один `GET /entity/productionstage?limit=1&offset=0` — только счётчик всех этапов и наличие ссылок на производственное задание и позицию в образце.

Оба запроса строго последовательные, без автоповтора, максимум 64 КиБ тела/ответ, тайм-аут 12 секунд каждый; на уровне браузера — 30 секунд. Уведомление в браузере не сохраняется в D1 или Git. Пароли, строки продукции и ID образцов не выдаются. Ошибка любого запроса запрещает показывать данные как полный охват.

При размере порции 50 (консервативная плановая величина, не настройка текущего API) возвращаем оценку числа страниц для двух реестров. Это **нижняя оценка запросов для чтения списков**, а не оценка времени или ресурсов для полного подтверждения статусов.

Даже наличие ссылки на задание в одном образце **не доказывает**, что все этапы можно надёжно сопоставить со всеми заданиями.

## Что нужно подтвердить перед настоящим сканером

1. Проверить доступность и корректность идентификатора связи `productionStage → productionTask`, `productionStage → productionRow` на нескольких известных заданиях, включая задание №00737. Не копировать образцы в публичный репозиторий.
2. Проверить, можно ли обойти реестр этапов по страницам и восстановить состояние каждого задания с учётом разных производственных позиций, неполных этапов, остановленного производства и возможных смешанных единиц.
3. Зафиксировать согласованную метку времени/срез, стратегию повторной проверки изменившихся документов, пагинации и дедупликации ID. `offset` при конкурентной вставке не гарантирует неизменяемый снимок. Нужна проверка полноты на конец цикла.
4. Оценить действующую нагрузку на API по отчёту «Статистика использования API». Документация описывает ограничения параллелизма/частоты; рассчитывать запас под уже работающие интеграции, не выходить на теоретический максимум.
5. Разделить состояния «незавершено», «подтверждённо завершено», «не удалось проверить» и «исключено/остановлено», если документ предоставляет основание для последнего. Непроверенное не равно нулю.
6. Доказать, что все активные задания включены; отдельно учитывать документы с отсутствующими сроками и производственными этапами.

## Будущий эксплуатационный контракт (НЕ включён сейчас)

- Сканирование выполняется только в отдельном задании с подтверждённым владельцем запуском, отдельным журналом этапов, квотами, паузой и возобновлением.
- До подтверждения нагрузочных лимитов стартовый бюджет: **не более 1 запроса/с**, последовательность, максимум 50 документов/пакет, без автоматических ретраев после 429/401/403.
- При неполном обходе, сетевой ошибке, конфликте метаданных или изменениях во время выгрузки отчёт получает статус «неполный», не публикуется как достоверная сводка всего цеха.
- Нельзя автоматически списывать материалы, менять задания/статусы, цены, Ozon/WB, Google Таблицу или рассылать уведомления.
- Для фактического запуска потребуются отдельная реализация журналирования, проверка на тестовой среде, контроль реальных вызовов и подтверждение публикации.

## Приёмка текущего этапа

- Owner-only, любые параметры пути отклоняются; отсутствующий/чужой пользователь не вызывает API.
- Ровно 2 последовательных upstream GET по `limit=1`; секрет не выходит в ответ.
- Ошибки/пустые данные и нестандартные ответы не превращаются в подтверждённый нулевой остаток.
- В интерфейсе нет автоматической синхронизации, cron, сохранения, сканирования всего реестра.
- CI проверяет API, интерфейс и прежние тесты монитора.


## Конкретный механизм полного обхода: два возможных пути (не запущено)

1. **Предпочтительный:** после проверки на реальном аккаунте прямых связей этап → задание → позиция прочитать реестр заданий и реестр этапов независимыми страницами (плановый размер 50), объединить по UUID задания и позиции, проверить план каждого этапа и отсутствие пропусков. Без этой проверки нельзя считать быстрый путь реализуемым.
2. **Резервный:** прочитать реестр заданий, затем запросить этапы по каждому заданию через уже существующий `production-stages?taskId=UUID`. Это минимум один запрос на каждое задание; задания с >50 этапами потребуют отдельной доработки постраничного чтения, иначе остаются «не подтверждено».
3. **Бюджет:** ограничить будущий сканер **одним одновременным запросом**, плановой паузой **не менее двух секунд** между стартами, пакетом **не более десяти GET**, без автоматического повтора после `429`, `401`, `403` или несогласованного ответа. Это консервативная проектная политика, а не гарантия отсутствия `429`: соседние интеграции расходуют общий бюджет. Перед запуском изучить CSV «Статистика запросов к API» в «МойСклад».
4. **Продолжение:** между пакетами фиксировать идентификатор цикла, прогресс, границы выборки, список обработанных UUID, счетчики успехов/ошибок и момент актуальности в тестовой D1. Нужны защита от двух одновременных сканеров и явная кнопка «Остановить». Секретные токены и персональные строки не переносить в логи.
5. **Достоверность:** по завершении сравнить исходные и конечные размеры коллекций, уникальность ID, связность этапов, перечень отсутствующих/дублированных/изменённых документов. При возможных изменениях во время offset-пагинации сделать контрольную повторную сверку. При любом пропуске показывать **неполный охват**, а не «все завершены».
6. **Обновления:** ежедневные инкременты/вебхуки проектировать только после доказательства поддерживаемых полей `updated` и механики подписки для этих сущностей. До этого полная повторная сверка по явному запуску, никакого Cron.

### Пример расчёта нагрузки — исключительно модель, не реальные данные аккаунта

При предположении **740 документов и 3700 этапов**:

| Вариант | Только минимальный первичный обход | Пакеты до 10 запросов |
| --- | ---: | ---: |
| Общий реестр заданий + этапов при подтверждённых связях | 15 + 74 = 89 GET | 9 |
| Отдельный запрос этапов на каждое задание | 15 + 740 = 755 GET или больше | минимум 76 |

Эти количества не включают повторные проверки, превышение 50 этапов на документ, сетевые ошибки и изменения записей во время сканирования. Объём 3700 этапов **взят для сценария**, фактическое количество ещё не получено. Расчёт формируется локальной чистой функцией `web/office/ms-production-scan-budget.mjs`, без внешних запросов. Настоящий сканер не создан.
