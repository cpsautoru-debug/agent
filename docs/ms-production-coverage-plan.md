# МойСклад — безопасная диагностика незавершённого производства

Статус: ручная диагностика готовится к выпуску после исправления HTTP 412; **полного сканера ещё нет**. Код API: `functions/api/ms/production-coverage-probe.js`. Источник — JSON API 1.2.

## Проверенное ограничение интерфейса API

20.11.2026 после успешной авторизации владелец получил `ms_upstream_error · productionstage · HTTP 412` при попытке прочитать `GET /entity/productionstage?limit=1&offset=0`.

В документации модели `ListProductionStagesOptions` поле фильтра `productionTask` **обязательно**. Код 412 в документации JSON API, среди прочего, означает отсутствие обязательного параметра.

Следовательно, получить глобальное число `productionstage` этим запросом нельзя. **Нельзя** суммировать этапы одного задания и представлять их как этапы всего цеха. Ранее рассмотренный быстрый вариант общего реестра этапов не подтверждён и **исключён из расчётов**.

Источники для проверки:
- API: https://dev.moysklad.ru/doc/api/remap/1.2/
- Типизированный клиент: https://jsr.io/@moysklad/moysklad-ts/doc (найти `ListProductionStagesOptions` и `SetRequired<FilterOptions<ProductionStageModel>, "productionTask">`).

## Контракт ручной диагностики

Защищённая кнопка `GET /api/ms/production-coverage-probe`:

1. Только после owner-session/проверки owner в D1: `GET /entity/productiontask?limit=1&offset=0`. Получить число заданий `meta.size` и один образец с проверенным UUID.
2. Если заданий **ноль**, второй запрос **не выполняется**. Это подтверждённое число заданий в момент ответа, но не общая верификация полноты производства.
3. Если есть задание с валидным UUID, строго последовательно выполнить `GET /entity/productionstage?limit=1&offset=0&filter=productionTask%3Dhttps%3A%2F%2Fapi.moysklad.ru%2Fapi%2Fremap%2F1.2%2Fentity%2Fproductiontask%2F<uuid>`. Значение фильтра создаётся на сервере из строго проверенного UUID; оно не приходит от браузера.
4. Показать только количество документов **всего**, количество этапов **только в одном образце задания**, факт наличия ссылок в образце и минимальную оценку числа запросов. **Глобальное число этапов всегда `null` (неизвестно)**.
5. Fail-closed: ошибка API/структуры прекращает цепочку, снаружи разрешены только `code`, `upstreamEntity`, `upstreamHttp` (HTTP 300–599 либо `null`). Никогда не выводить тексты ошибок, сырые строки, ID, имена товаров, персональные сведения или bearer-токен.

Ограничения: до двух последовательных GET, каждый `limit=1`, без автоповтора, без расписания, без записи в «МойСклад» или D1; ответ не более 64 КиБ, запрос до 12 сек, клиентский тайм-аут 30 сек.

## Реальный путь полного охвата — только как отдельный будущий этап

- Первый реестр: страницы `productiontask` по 50, уникальные UUID, сортировка/граница и повторная сверка после загрузки.
- Второй этап: **по каждому** заданию отдельный `productionstage?filter=productionTask=<href>`, строго последовательно. Если у задания более 50 этапов, требуется постраничный обход его этапов. Существующий `production-stages?taskId=UUID` рассчитан только на задачи до 50 этапов и не является готовым полным сканером.
- При отсутствии этапов, неоднозначном статусе, остановленном производстве, незавершённых заданиях без плановой даты, частичных выполнениях, ошибке связи или конфликте данных результат отмечается как «не проверено», а не как ноль или «всё готово».
- Объём готовой продукции определять по финальному этапу каждой производственной позиции. Не суммировать последовательные этапы как независимые комплекты.
- Нельзя считать проведённое задание выполненным; финансовые/материальные движения не запускать.

**Плановое ограничение будущего сканера:** 1 запрос одновременно, пауза минимум 2 секунды между запросами, максимум 10 GET на пакет, остановка на 429/401/403 или неполном ответе. Это консервативный план, **не гарантия** отсутствия ограничений на общем аккаунте. Потребуются счётчик выполнения, возобновление, журнал ошибок и контроль изменившихся во время обхода документов. До реализации и одобрения не запускать.

### Модель нагрузки (числа ниже не из реального аккаунта)

Допустим, документов 740, размер страницы 50. Потребуется минимум `ceil(740/50) + 740 = 755` GET, то есть **не менее 76 пакетов по 10**. Если есть задания с более чем 50 этапами, запросов будет больше. Общее число этапов неизвестно. Эти числа — **пример**, не реальная статистика «МойСклад».

Функция расчёта: `web/office/ms-production-scan-budget.mjs`. Она ничего не читает и не меняет.

## Приёмка очередного выпуска

- Unit/CI: запрос этапов с **обязательным фильтром по UUID образца**, не более 2 последовательных запросов; отсутствие второго запроса при 0 заданиях; отказ при невалидном UUID.
- Unit/CI: `totalProductionStages:null`, `globalStageListAvailable:false`, `allUnfinishedVerified:false`; пример одного задания не выглядит как глобальная сводка.
- Строгая owner-авторизация, URI, Content-Type, размер ответа, ошибки и ограничения сохранены.
- Проверить реальный тестовый офис: анонимный GET — 401 JSON, обновлённый JS — HTTP 200; затем **один** авторизованный ручной запуск с фиксацией только агрегатов и статуса.
- Не запускать полный обход, не писать в МойСклад, D1, WB/Ozon/Яндекс, Google Таблицу, Workers/Cron. Продолжать стратегию 90 дней через контроль достоверности данных.

## Следующая контрольная точка

После успешного owner-probe получить фактическое количество заданий и количество этапов **одного** задания. Тогда оценить реальную нижнюю нагрузку `ceil(N/50)+N` и спроектировать минимальный безопасный сканер в отдельной ветке: одна страница → подтверждение источников → журнал полноты → ограниченный пакетный обход. Временной срез обязательно контролировать, иначе получаем несогласованную статистику.

## Первый успешный реальный срез и следующий gate — 20.11.2026

Владелец выполнил **один** ручной owner-only запуск диагностики в опубликованном офисе. Получены агрегаты:

- **744 производственных задания в реестре**: `totalTaskDocuments`.
- **45 этапов в одном образце задания**: `sampleTaskStageCount`; глобальное число этапов неизвестно.
- Есть ссылка на производственную позицию, но прямая ссылка `productionTask` в образце этапа отсутствует. Это **не** означает, что связь потеряна: принадлежность может быть закодирована внутри `productionRow.meta.href`.
- Нижняя нагрузка для полного обхода: `ceil(744/50)+744=759` GET, не менее **76 пакетов по 10**. Дополнительные страницы этапов, проверка непротиворечивости данных и задержки не включены. При 2 сек между запросами только техническая пауза составит минимум около 25 минут, поэтому выполнять полный обход одним запросом Cloudflare Worker нельзя.

### Минимальное дополнительное доказательство связи (без новых запросов)

Отдельное безопасное изменение: в образце проверять, содержит ли `productionRow.meta.href` канонический путь вида `/entity/productiontask/<task UUID>/productionRows/<row UUID>`. Если вложенный UUID **равен** UUID задания, использованному в обязательном `productionTask`-фильтре, выдавать `sampleRowTaskMatch: matched`. Если нельзя достоверно прочитать такого вложенного родителя — `not_observed`. Если родитель указан, но UUID **другой**, завершить ответ ошибкой `ms_response_unverified` без раскрытия ссылок/ID/данных. `bulkStageJoinProven:false` и `allUnfinishedVerified:false` сохраняются всегда.

Это доказательство **только для одного образца**; оно не подтверждает другие задания и не включает сканирование. После публикации достаточно **одного** ручного диагностического нажатия и затем отдельного пилота на пяти заданиях с проверкой ограничений. Полный сканер по-прежнему не включён.
