# АвтоСклад63: финансовая аналитика WB по артикулам и подготовка общего P&L с Ozon

Дата: 2026-11-21. Только staging, без изменения исходных финансовых отчётов.

## Что подтверждено и что пока отсутствует

Финансовая база WB содержит отчёты с номерами, периодами, итоговыми выплатами, статусом сверки, а также операции с артикулом vendor_code, количеством, продажами, возвратами, логистикой, хранением, удержаниями и штрафами.

Новый API /api/wb/unit-economics читает исключительно завершённые и сверенные отчёты. Сумма группированных финансовых строк обязана совпадать с подтверждённой выплатой — иначе ответ блокируется. Незавершённые отчёты не включаются в расчёт. Строки без артикула и их удержания остаются отдельной суммой, не назначаются другому изделию.

На момент последнего скриншота владельца в WB было 16 отчётов, из них 10 complete и 6 pending, 1020 операций. Это не обещание текущих цифр: панель берёт фактические данные из D1.

Вклад после известных затрат — не чистая прибыль. Итоговая прибыль по артикулу отсутствует до подтверждения рекламных расходов, налоговой базы, распределения общих затрат и возвратов. Период WB состоит из недельных отчётов, которые могут пересекать месяцы; без дат в строках API это не закрытый календарный P&L.

## Состав себестоимости

Себестоимость авточехлов = материалы + зарплата швеи + зарплата закройщика, по подтверждённой техкарте модели.

Упаковщик, водитель, управляющий, ОТК, аренда, вывоз мусора, связь, коммунальные услуги и офисные сервисы — отдельные накладные расходы. Они не должны второй раз попадать в стоимость комплекта. Реклама относится к отдельным расходам по каналу, налог — к налогоплательщику и подтверждённой налоговой базе, а не к банковской выплате.

Не переносить себестоимость Ozon SKU на WB vendor_code без проверки точной модели/артикула.

## Одно ручное действие перед ведением цен

Только после успешной публикации Pages применить файл migrations/wb/0007_wb_profit_unit_costs.sql к базе autosklad63-wb-reports-staging:

1. Cloudflare Dashboard → Storage & databases → D1 SQL Database.
2. Открыть ИМЕННО autosklad63-wb-reports-staging, а не производственную D1 и не Ozon.
3. Открыть Console; скопировать полный SQL из указанного файла ветки feature/marketplace-agents-staging в GitHub.
4. Выполнить скрипт один раз. Таблица, индекс и два защитных триггера создаются дополнительно (IF NOT EXISTS).
5. Вернуться в онлайн-офис → Финансы WB → Результат по каждому артикулу WB. Обновить страницу и сверить статус справочника.

До применения миграции панель должна показывать артикулы с отсутствующей себестоимостью. Форма записи стоимости будет недоступна; это ожидаемо, сам монитор WB продолжает работать.

В форме себестоимости после миграции:
- выбрать точный WB артикул из уже сохранённых финансовых операций;
- указать себестоимость одной единицы, дату начала действия и основание;
- предварительное/подтверждённое значение указать осознанно, подтвердить состав;
- нажать «Проверить запись», затем отдельной кнопкой сохранить;
- цены хранятся в истории по дате, исходные строки WB и выплаты не меняются.

Если цена менялась посреди недельного отчёта, расчёт себестоимости этого отчёта не объявляется подтверждённым из-за отсутствия точной даты каждой операции. Нельзя переписывать существующие записи цен задним числом.

## Привязка общих расходов, WB и Ozon

Источником общих расходов должен стать один утверждённый реестр, а не два одинаковых расхода в WB и Ozon. Существующий Ozon Profit уже имеет версионный документ expenses с общими и Ozon-расходами; перед общей интеграцией нужно сверить его содержимое и назначение.

Категории: зарплаты упаковщика, водителя, управляющего, ОТК; аренда; коммунальные платежи; вывоз мусора; связь; ПО и другие накладные расходы. У каждого расхода — первичный документ, сумма, месяц, юридическое лицо, признак включения в себестоимость и способ распределения.

Модель ABC: зарплата упаковщика — по подтверждённой упаковочной нагрузке; водитель — по подтверждённым рейсам/отгрузкам; общая аренда — по обоснованному ключу; управленческие затраты — по утверждённым долям. Пока ключ не подтверждён, показывать расход как нераспределённый, а не подставлять произвольную долю.

В репозитории создан чистый модуль shared-overheads-core.mjs, который распределяет только подтверждённые суммы без потери копеек между WB/Ozon/Яндекс/Авито/розницей. В живой D1 он ещё не подключён — это следующий этап общего финансового реестра.

### Реклама и налог

Рекламные расходы WB должны приходить из рекламного API/реестра с датой и кампанией, со сверкой, чтобы не вычитать дважды суммы, уже включённые в удержания WB Finance. Пока этого нет, чистая прибыль остаётся не рассчитанной.

Для WB и Ozon не объединять налоговые ставки и юрлица без документов. На прежних настройках WB использовалась АУСН «доходы 8%», для другого кабинета Ozon мог действовать иной субъект и режим. Налог нельзя автоматически считать процентом от банковской выплаты WB. Нужен подтверждённый налоговый регистр по налогоплательщику, возвратам, расходным операциям и месяцу.

## Контроль приёмки

- GET /api/wb/unit-economics доступен владельцу, анонимному посетителю возвращает 401.
- Сумма завершённых отчётов и групповых операций совпадает, иначе расчёт не возвращается.
- В интерфейсе видны коды WB, проданные и возвращённые единицы, выплаты, удержания, подтверждённые производственные затраты и отсутствующие исходные данные.
- Чистая прибыль остаётся «Не рассчитана», пока отсутствуют налог, реклама, общие расходы или неподтверждённые возвраты.
- Миграция не меняет ни один старый отчёт, а запись новой себестоимости идёт через подписанный предпросмотр владельца.
- Worker WB, Cron, существующая база отчётов и Ozon-операции остаются без изменений.
