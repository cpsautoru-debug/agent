# АвтоСклад63 — автономная проверка производства в Cloudflare (staging)

## Статус на 20.11.2026

**Код подготовлен, но реальный Cloudflare Cron и D1 ещё НЕ запущены.** Эта ветка создаёт staging-only Worker-код, чистую миграцию изолированной D1 и тестовый контракт. Публикация Pages по GitHub не разворачивает новый Scheduled Worker. Нельзя писать пользователю «сканирование уже круглосуточно работает» до подтверждения его Cloudflare deployment и реальных первых запусков.

Причина: на облачной стороне требуется создать/привязать **отдельную** D1 и секрет **`MS_API_TOKEN`** в контекст Worker. Токен уже существует в Pages, но это не подтверждение, что он привязан к новому Worker. При отсутствии доступа на изменение аккаунта Cloudflare нельзя угадывать идентификаторы ресурсов или переносить токен в GitHub.

## Архитектура без ручных номеров

1. Cloudflare Scheduled Worker (отдельно от Pages) запускается примерно каждые 5 минут с флагом `MS_PRODUCTION_AUTO_SYNC=enabled` и владельцу не нужно открывать вкладку.
2. Использует **только GET** в JSON API «МойСклад»: 1 запрос страницы `productiontask` с `limit=5&offset=<cursor>&order=moment,asc`, затем по 1 **обязательно отфильтрованному** запросу `productionstage` на каждое задание, `limit=50`.
3. **Не более 6 внешних GET за запуск, строго последовательно, пауза 2 с**. При 429 / 401 / 403 / transport-error все новые запросы немедленно прекращаются; курсор не продвигается. Не отправлять повторно десятки запросов за один запуск.
4. В отдельной D1 таблице записываются поколение скана, курсор, исходное число документов, документный номер и безопасные агрегаты по этапам. **Никаких записей в «МойСклад»**, не создаём задания, не переводим этапы, не списываем материал и не трогаем финансовую D1.
5. Если этапов больше 50, формат связи не распознан или цепочка противоречива, статус **`unverified`**. Никаких фиктивных комплектов и выработки.
6. По окончании перехода через исторический реестр состояние помечается `pass_complete` — это значит **завершён один проход по документам**, а **не** доказано, что состояние единовременно синхронно или что найдено всё незавершённое производство. Для доказуемого live-портфеля нужна проверка полноты, перемещений во время сканирования, технологических цепочек и срока актуальности.
7. При следующем тике начинается новое поколение с курсором 0. Актуальный просмотр должен показывать дату и поколение, чтобы не смешивать данные разных поколений.

При 744 исторических заданиях минимально 149 срабатываний по 5 документов, то есть примерно 12 часов при расписании раз в 5 минут (без дополнительных ошибок/стадийных страниц). Это **не realtime**. Для сокращения задержки в будущем использовать подтверждённые статусы/вебхуки и отдельный быстрый путь последних изменений, но пока не выдавать изменения за полный список.

## Данные и привилегии

- SQL: `migrations/ms/0001_ms_production_autosync_staging.sql`. Выполнять только в созданной для производственного мониторинга staging D1.
- Код: `workers/ms-production-autosync.js`. Экспортирует только scheduled handler; **нет публичного HTTP endpoint**.
- Шаблон: `wrangler.ms-production-autosync-staging.example.jsonc`, с безопасным `MS_PRODUCTION_AUTO_SYNC=disabled`. До привязки D1 и секрета не запускать. Секрет не в GitHub.
- Доступ к данным D1 через Pages API нужен отдельно, с проверкой владельца по действующей сессии. Пока интерфейс браузера использует существующий owner-only API и сам обновляет последние данные; новый Cron **не** считается действующим источником цифр.
- Не использовать финансовые D1 Ozon/WB в качестве базы производства. Старые SQL-таблицы и отчёты не менять.

## Безопасный выпуск после восстановления доступа к Cloudflare

1. Создать отдельную staging D1, применить SQL миграцию, убедиться что таблицы пусты и runtime имеет `generation=0,next_offset=0,run_status=new`.
2. Развернуть Worker с `workers_dev:false` и без публичного HTTP маршрута; привязать только staging D1 и `MS_API_TOKEN` в Secret, без раскрытия значения действующего Pages secret: повторно ввести действующий токен либо создать отдельный read-only токен.
3. Проверить отключённый флаг: 0 исходящих GET; включить в staging только по подтверждённому плану API нагрузки.
4. Проверить первые 2 cron-запуска, лимит GET, 2-секундные интервалы, прогресс курсора и отсутствие 429. Проверить контрольный failure 429 на синтетике, а не на рабочем API.
5. Проверить schema/агрегирование >50 этапов, смену `meta.size` во время скана, пропуск/дубли. Только после этого подключать защищённый read-only endpoint статуса в панели CTO.
6. Полный запуск и собственно production Cron — отдельная операционная активация. Никаких неконтролируемых 759 GET одним HTTP-запросом.

Критерий приёмки: GitHub CI проходит unit + SQL schema; Cloudflare лог фиксирует номер поколения, offset, число запросов и безопасный код результата без ID/токена/имён в публичных журналах. Только после успешного живого staging теста допускаются KPI производственной очереди. Если доступ к Cloudflare отсутствует, **задача остаётся подготовленной, но не выполненной**, даже при зеленом CI.

## Следующий этап: чтение результатов в онлайн-офисе без Cloudflare-операций

Для автоматического производственного сканера подготовлен owner-only API `GET /api/ms/production-auto-status` в Pages и браузерный блок **«Фоновый мониторинг производственного реестра»**. Это **код**, а не подтверждение развёрнутого Cron.

Контракт:
- Сначала проверяет `verifySession` и таблицу владельца в действующей auth-D1, затем читает только отдельно привязанную `MS_PRODUCTION_DB` (никаких операций записи). Без владельца — HTTP 401/403; без привязки — HTTP 503 `ms_auto_storage_not_configured`. Не принимает параметры, генерацию или произвольный SQL от клиента.
- Из таблицы runtime читает поколение, положение курсора, размер исторического реестра, состояние проверки, время последнего успешного пакета и безопасный код ошибки.
- Считает в рамках **одного** поколения документы с `complete`, `incomplete`, `unverified`. Из них только до 20 исторически незавершённых выводятся в таблицу, без UUID и приватных upstream данных в клиентском JSON.
- `completeHistoricalPass` допустимо только если `run_status=pass_complete`, `next_offset >= total_first_seen` и число проверенных документов совпало с контрольным размером. Это **не** подтверждение, что все эти задания сейчас активны или что их статусы были проверены одновременно. Индикатор давности последнего успешного пакета — меньше/больше 24 часов.
- Интерфейс читает статус автоматически только на видимой вкладке `#production` и не чаще раза в 30 минут; ручное обновление сохранено как запасное. При неподключённой D1 или неверных данных не создаёт фиктивные нулевые показатели.
- Документы, счета, изменения складских остатков, API токены, финансовые D1 и Cron не изменяются. Для выполнения 24/7 нужно отдельно привязать выделенную D1 к Pages Functions и развернуть ранее подготовленный Worker, включить расписание и подтвердить реальные первые сканирования в разрешённой среде.

**Критерии приёмки без доступа к Cloudflare:** новые unit/UI tests + GitHub Actions, проверка запросов владельца и некорректных/неполных исторических данных. Реальную работу с живой D1 пока нельзя подтвердить и нельзя объявлять запущенной.

## Защита от смещения реестра во время обхода

При постраничном историческом сканировании новые производственные документы могут появляться, пока курсор движется. Поэтому:
- Сканер **отвергает неполную страницу** (например, 2 документа вместо ожидаемых 5), не запрашивая этапы и не продвигая курсор.
- Число документов `meta.size` сверяется с числом, полученным в начале текущего поколения. **Любое увеличение или уменьшение** останавливает пакет с кодом `ms_auto_source_count_changed` без записи частичных результатов.
- На **следующем разрешённом запуске** после такого кода автоматически открывается новое поколение с `offset=0`, чтобы не требовать ручного сброса курсора; действующие ограничения 5 заданий / 6 GET / паузы остаются.
- Результаты разных поколений нельзя смешивать. Даже завершённое поколение не гарантирует транзакционно одновременного статуса всех заданий; дополнительная защита read API сверяет число сохранённых уникальных заданий и контролируемое число документов.

Приёмка без Cloudflare: unit-тесты на пропущенную страницу, увеличение/уменьшение реестра, автоматический перезапуск нового поколения, запрет переноса некорректного курсора. Реальный Cron и подключение D1 по-прежнему требуют отдельной активации и в этой задаче не проверяются.

## Важно: существующий Pages secret нельзя скопировать из Cloudflare

Cloudflare не предоставляет значение ранее сохранённого encrypted secret обратно через UI/API. Поэтому **наличие `MS_API_TOKEN` в Pages не означает, что его можно автоматически извлечь для нового Worker**. Нельзя читать этот токен из GitHub, логов, HTML или обходить ограничения аккаунта.

Чтобы включить новый Scheduled Worker, токен `MS_API_TOKEN` придётся **один раз безопасно ввести** в настройках Worker или с локального терминала через `wrangler secret put MS_API_TOKEN --config <локальный-config.jsonc>`. Токен вводится в скрытом prompt, не в чат, репозиторий или командную строку. Если актуальное значение недоступно, создать отдельный read-only API-токен в «МойСклад» с минимально нужными правами, затем хранить его только как Worker secret. Не перезаписывать действующий Pages token.

## Запуск через Codex на компьютере владельца (после подтверждённого входа Cloudflare)

Codex работает с текущим кодом `feature/marketplace-agents-staging` и может выполнить локальные команды. Прежде чем создавать ресурсы, он обязан проверить активный аккаунт и получить его разрешение на одну операцию с секретом в интерактивном prompt. Все действия только для **staging**; production и финансовые базы не трогать.

1. `npx wrangler whoami` — удостовериться, что вошли в правильный аккаунт; если не вошли, открыть штатную авторизацию.
2. Просмотреть `npx wrangler d1 list` и настройки проекта Pages, не использовать чужую/финансовую D1. Если отдельной `autosklad63-ms-production-staging` нет — создать её через `npx wrangler d1 create autosklad63-ms-production-staging`, сохранить новый UUID локально без токенов.
3. Скопировать `wrangler.ms-production-autosync-staging.example.jsonc` во **вневерсионный** локальный файл, добавить `d1_databases` с binding `MS_PRODUCTION_DB`, названием и действительным ID именно созданной staging D1. Исходный example и любые секреты в GitHub не менять.
4. Выполнить миграцию `migrations/ms/0001_ms_production_autosync_staging.sql` **только** в выделенной D1 через `wrangler d1 execute ... --remote --file ...`. Убедиться в начальной runtime-строке и отсутствии производственных данных до сканирования.
5. Развернуть Worker с `MS_PRODUCTION_AUTO_SYNC=disabled`; сохранить `workers_dev=false`, Cron `*/5 * * * *` и лимит 6 последовательных GET. Ввести `MS_API_TOKEN` **без раскрытия** через Worker secret. Проверить, что секрет существует, не читать его значение.
6. На Pages staging привязать ту же выделенную D1 с именем `MS_PRODUCTION_DB` для `/api/ms/production-auto-status`. Не менять binding `OZON_FINANCE_DB` и другие существующие bindings. Учесть необходимость нового деплоя Pages после изменения binding.
7. Включить флаг в Worker после прохождения тестов/проверки доступа и выполнить два безопасных Cron-тика. Проверить курсор, 6 GET максимум, паузы, отсутствие 429, даты и правдоподобие счётчиков. Не включать автоматическое списание материалов и не объявлять все 744 задания активными.
8. Убедиться, что `#production` в офисе при owner-сессии читает данные D1, а публичный доступ возвращает 401. Не выводить в лог токены, customer-data и UUID. В случае проблем вернуть флаг `disabled`, сохранить отчёт без секретов.

**Операционная приёмка:** `MS_PRODUCTION_DB` существует и привязана к Worker/Pages; секрет в Worker установлен, Cron выполняет два реальных тика, курсор увеличивается, статус в защищённом офисе виден. Если какая-то зависимость недоступна — помечать как блокер, не подменять успехом тестов GitHub.
