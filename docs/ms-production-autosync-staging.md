# АвтоСклад63 — автономная проверка производства в Cloudflare (staging)

## Статус на 20.11.2026

**Код подготовлен, но реальный Cloudflare Cron и D1 ещё НЕ запущены.** Эта ветка создаёт staging-only Worker-код, чистую миграцию изолированной D1 и тестовый контракт. Публикация Pages по GitHub не разворачивает новый Scheduled Worker. Нельзя писать пользователю «сканирование уже круглосуточно работает» до подтверждения его Cloudflare deployment и реальных первых запусков.

Причина: на облачной стороне требуется создать/привязать **отдельную** D1 и секрет **`MS_API_TOKEN`** в контекст Worker. Токен уже существует в Pages, но это не подтверждение, что он привязан к новому Worker. При отсутствии доступа на изменение аккаунта Cloudflare нельзя угадывать идентификаторы ресурсов или переносить токен в GitHub.

## Архитектура без ручных номеров

1. Cloudflare Scheduled Worker (отдельно от Pages) запускается примерно каждые 5 минут с флагом `MS_PRODUCTION_AUTO_SYNC=enabled` и владельцу не нужно открывать вкладку.
2. Использует **только GET** в JSON API «МойСклад»: 1 запрос страницы `productiontask` с `limit=5&offset=<cursor>&order=moment,asc`, затем по 1 **обязательно отфильтрованному** запросу `productionstage` на каждое задание, `limit=50`.
3. **Не более 6 внешних GET за запуск, строго последовательно, пауза 2 с**. При 429 / 401 / 403 / transport-error все новые запросы немедленно прекращаются; курсор не продвигается. Не отправлять повторно десятки запросов за один запуск.
4. В отдельной D1 таблице записываются поколение скана, курсор, исходное число документов, документный номер и безопасные агрегаты по этапам. **Никаких записей в «МойСклад»**, не создаём задания, не переводим этапы, не списываем материал и не трогаем финансовую D1.
5. Если этапов больше 50, формат связи не распознан или цепочка противоречива, статус **`unverified`**. Никаких фиктивных комплектов и выработки.
6. По окончании перехода через исторический реестр состояние помечается `pass_complete` — это значит **завершён один проход по документам**, а **не** доказано, что состояние единовременно синхронно или что найдено всё незавершённое производство. Для доказуемого live-портфеля нужна проверка полноты, перемещений во время сканирования, технологических цепочек и срока актуальности.
7. При следующем тике начинается новое поколение с курсором 0. Актуальный просмотр должен показывать дату и поколение, чтобы не смешивать данные разных поколений.

При 744 исторических заданиях минимально 149 срабатываний по 5 документов, то есть примерно 12 часов при расписании раз в 5 минут (без дополнительных ошибок/стадийных страниц). Это **не realtime**. Для сокращения задержки в будущем использовать подтверждённые статусы/вебхуки и отдельный быстрый путь последних изменений, но пока не выдавать изменения за полный список.

## Данные и привилегии

- SQL: `migrations/ms/0001_ms_production_autosync_staging.sql`. Выполнять только в созданной для производственного мониторинга staging D1.
- Код: `workers/ms-production-autosync.js`. Экспортирует только scheduled handler; **нет публичного HTTP endpoint**.
- Шаблон: `wrangler.ms-production-autosync-staging.example.jsonc`, с безопасным `MS_PRODUCTION_AUTO_SYNC=disabled`. До привязки D1 и секрета не запускать. Секрет не в GitHub.
- Доступ к данным D1 через Pages API нужен отдельно, с проверкой владельца по действующей сессии. Пока интерфейс браузера использует существующий owner-only API и сам обновляет последние данные; новый Cron **не** считается действующим источником цифр.
- Не использовать финансовые D1 Ozon/WB в качестве базы производства. Старые SQL-таблицы и отчёты не менять.

## Безопасный выпуск после восстановления доступа к Cloudflare

1. Создать отдельную staging D1, применить SQL миграцию, убедиться что таблицы пусты и runtime имеет `generation=0,next_offset=0,run_status=new`.
2. Развернуть Worker с `workers_dev:false` и без публичного HTTP маршрута; привязать только staging D1 и `MS_API_TOKEN` в Secret, прочитав из действующего облачного секрета без его копирования в переписку/репозиторий.
3. Проверить отключённый флаг: 0 исходящих GET; включить в staging только по подтверждённому плану API нагрузки.
4. Проверить первые 2 cron-запуска, лимит GET, 2-секундные интервалы, прогресс курсора и отсутствие 429. Проверить контрольный failure 429 на синтетике, а не на рабочем API.
5. Проверить schema/агрегирование >50 этапов, смену `meta.size` во время скана, пропуск/дубли. Только после этого подключать защищённый read-only endpoint статуса в панели CTO.
6. Полный запуск и собственно production Cron — отдельная операционная активация. Никаких неконтролируемых 759 GET одним HTTP-запросом.

Критерий приёмки: GitHub CI проходит unit + SQL schema; Cloudflare лог фиксирует номер поколения, offset, число запросов и безопасный код результата без ID/токена/имён в публичных журналах. Только после успешного живого staging теста допускаются KPI производственной очереди. Если доступ к Cloudflare отсутствует, **задача остаётся подготовленной, но не выполненной**, даже при зеленом CI.
