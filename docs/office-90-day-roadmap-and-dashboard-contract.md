# АвтоСклад63 — единый 90-дневный план онлайн-офиса

**Статус:** рабочая архитектура, 23 ноября 2026. Этот документ фиксирует исходный приоритет, а не объявляет остальные направления завершёнными.

## Управленческое правило

Пульт руководителя — **витрина состояния единой системы**, а не самостоятельная база данных. Все модули: «МойСклад», Ozon, Wildberries, Яндекс Маркет, Авито, сайт autosklad63.ru, офлайн-магазин, социальные сети и ИИ-агенты — подключаются к **своему источнику истины** и публикуют проверенные состояния через авторизованные API. Дашборд только читает. Никаких ручных номеров заданий, повторного ввода остатков или копий финансовых показателей внутри дашборда.

## Порядок внедрения (без параллельного распыления ресурсов)

### Этап 1 · Производство, склад и процессы

- [ ] Автоматический сбор **всех** текущих производственных заданий через API МойСклад (с курсором, ограничением частоты, ретраями и диагностикой).
- [ ] Определение реальной очереди по производственным этапам: раскрой, пошив, ОТК, упаковка, готово; исключение завершённых и отменённых.
- [ ] Два физических склада: остатки, отрицательные позиции, поступления, перемещения, списание по технологическим картам, сигналы нехватки материалов.
- [ ] Карточка заказа: ответственный, сроки, потребность в материалах, отклонения по качеству, фактическая дата перехода этапа.
- [ ] Дашборд: число **активных** заданий (только после подтверждения актуальности), просрочка, загрузка, остатки и критические ошибки.
- **Критерий приёмки:** совпадение текущей очереди, этапов и остатков с МойСклад на контрольном наборе и без ручного копирования номеров. Исторический сканер **не** равен живой очереди.

### Этап 2 · Финансы и продажи

- [ ] Ozon Seller/Finance + Performance: сверка начислений, комиссий, рекламы, логистики, возвратов, себестоимости по SKU, налога и выплат банка за закрытый период. Исключить двойные списания. Учитывать разные кабинеты и юрлица.
- [ ] Wildberries: полный перечень отчётов и сверка операций с выплатами, реклама, возвраты, себестоимость и налоги; закрыть обнаруженные расхождения.
- [ ] Яндекс Маркет, Авито, торговая точка «Пламя»: подключения, единая нормализация заказов, каналов и выручки.
- [ ] Единый журнал операций с дедупликацией по **источнику, аккаунту, типу и внешнему ID**, отдельные факты выручки, затрат, выплат и налогов.
- [ ] Прибыль по SKU, каналу, кабинету и компании; общий результат только после сверки и закрытия всех требуемых источников.
- [ ] Дашборд: выручка, заказы, прибыль, ДРР, возвраты, неоплаченные заказы, расхождения с **периодом, источником и статусом подтверждения**.
- **Критерий приёмки:** контроль одного закрытого периода до рубля с отчётом маркетплейса, журналом начислений и банковской выпиской; объяснённые расхождения. Чистую прибыль не маркировать «подтверждённой» до закрытия всех зависимостей.

### Этап 3 · Агенты, сайт, продвижение и управление

- [ ] ИИ-диспетчер производства: только рекомендации и маршрутизация поручений после контрольной сверки.
- [ ] Складской агент, финансовый аналитик, аналитик продаж, CEO-ассистент: отдельные разрешения на чтение/запись, журнал действий, лимиты API, подтверждение рискованных операций.
- [ ] Сайт autosklad63.ru: CMS, формы, конверсии, Метрика, SEO и публикации через проверенный релиз; никакой несанкционированной автопубликации.
- [ ] Монитор соцсетей и рекламы: публикации, охваты, заявки, расходы и атрибуция. Подключить Авито и сообщения/лиды только по реально доступным API.
- [ ] Дашборд: поручения/исключения, инциденты, маркетинг, воронка сайта и эффективность каналов.
- **Критерий приёмки:** агенты читают реальные источники; каждое действие имеет владельца, аудит и отмену/ручное подтверждение для опасных операций.

## Контракт интеграции для каждого нового модуля

1. **Источник истины:** система, кабинет, юрлицо, API и полномочия доступа; ключи — только в Cloudflare Secrets.
2. **Данные:** `source_id`, `account_id`, `metric_id`, `period_start`, `period_end`, `unit`, `value`, `observed_at`, `ingested_at`, `source_record_id`, `coverage`, `verification_status`, `errors`. Значения денег — целые копейки, не float.
3. **Состояния:** `planned`, `partial`, `blocked`, `verified`; никаких «0» вместо отсутствующей метрики. `verified` допустимо только после сверки и выполнения контрольных условий конкретного модуля.
4. **Свежесть:** у каждой карточки свой timestamp. Исторические записи, live-очередь, продажи за месяц и отчёты WB по всей истории не смешиваются.
5. **Безопасность:** GET для дашборда и только owner-auth; API-токены не выдавать браузеру; личные данные не публиковать; внешний API с лимитами, таймаутами и безопасным диагностическим сообщением.
6. **Приёмка:** тест сценариев успеха/неполноты/ошибки/нет прав, сверка первоисточника, демонстрация на staging, затем виджет дашборда из **того же API**, без второго учётного слоя.
7. **Никакой записи из витрины**: команды и изменения выполняются в отдельном маршруте с подтверждением, аудитом и контролем идемпотентности.

## Дашборд и источники

`web/office/office-source-registry.mjs` хранит неизменяемый перечень направлений и отображает их статус в пульте руководителя. Существующие карточки читают API Ozon/WB/МойСклад. Новые модули добавляются в реестр и публикуют свой **валидированный** статус, после чего данные становятся доступны на том же экране. Реестр не заменяет сам источник и не доказывает корректность финансов.

### Текущие ограничения на 23 ноября

- Ozon Performance API и денежные поля возвращаются; **сверка с Ozon Finance и банком не завершена**.
- WB: отчёты частично обработаны; **чистая прибыль не подтверждена**, есть расхождения.
- МойСклад: исторический монитор работает; **полная живая очередь и двухскладская сверка не подтверждены**.
- Яндекс, Авито, офлайн и соцсети: реальный единый финансовый/операционный API пока не доказан.
- Пульт руководителя не должен подменять эти ограничения красивыми цифрами.

## Правило управления изменениями

Каждая задача в GitHub относится к одному этапу и указывает: входной источник, проверяемый результат, владельца, отказоустойчивость, тест, изменения в интерфейсе и критерии приёмки. Сначала исправляем базовый источник/модуль, **в той же задаче** обновляем статус/показатели дашборда. Так дашборд всегда следует за развитием системы, а не уводит от плана.
