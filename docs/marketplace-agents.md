# Продажи маркетплейсов — план подключения

Решение владельца от 18.10.2026: добавить в отдел продаж агентов ВБ и Ozon, перенести туда Instagram. Задачи маркетплейсов: отзывы, наблюдение за акциями и продажами, передача заказов менеджеру для записи в рабочую Google Таблицу.

Ответственные: разработчик подключает API; агент площадки получает события и готовит ответы; менеджер продаж сверяет и записывает заказ. Роль в офисе не означает работающий сервис.

Обязательные входы: кабинет продавца и схема работы, права API для нужных данных, сопоставление артикулов с товарами таблицы, дата начала импорта, правила обработки отмен и возвратов. Секреты вводятся в защищённые настройки сервера, не в чат и не в Git.

Контракт передачи: площадка, внешний ID заказа/отправления, ID позиции, дата события и получения, артикул, количество, статус, валюта и подтверждённые суммы, ссылка/тип источника. Неизвестные суммы не заменять нулём; заказ, продажа, выручка и фактическая оплата — разные события.

Менеджер перед записью проверяет уникальность ключа «площадка + внешний ID + позиция», перечитывает строку и сохраняет формулы таблицы. Повтор синхронизации обновляет статус существующей записи. Отмена не удаляет историю; возврат связан с исходной записью. Исторический импорт — только за согласованный период. Расход материалов не списывается повторно из-за добавления заказа.

Отзывы: сначала проверяемые черновики с фактами из базы. Автопубликация требует согласования правил и полномочий. Акции: мониторинг условий и предложение владельцу; не вступать в акции и не менять цены автоматически.

Ожидаемый результат подключения заказов: реальные события приходят в закрытую очередь, менеджер добавляет заказ один раз. Критерий приёмки: проверены новый заказ, повтор события, изменение статуса, отмена, ошибка API и возобновление после ошибки; есть журнал и уведомление владельцу. API маркетплейсов для заказов и очередь не подключены. Финансовая интеграция Ozon Seller API ведётся отдельно; путь обычной синхронизации защищён проверкой роли владельца и D1-блокировкой. Плановый Cron `0 6 * * *` UTC в тестовом Worker подготовлен, но выключен до отдельного разрешения владельца.

## Сверка начислений Ozon

Локальный механизм в `functions/api/ozon/reconciliation.js` разделяет сверку одного дня на два уровня. Нетто-сверка сравнивает дату, внешний идентификатор отправления/услуги и итог группы в копейках с агрегированным `total_amount` API. Группы и строки источников имеют разную гранулярность; идентификатор строки Excel не считается `accrual_id` Seller API. Положительные и отрицательные суммы разных представлений сохраняются для контроля, но не должны совпадать, если одна сторона показывает валовую детализацию, а другая — нетто-начисление.

Детальная сверка отдельно требует проверенного взаимно-однозначного сопоставления дохода, комиссии, логистики и остальных компонентов. Вложенные суммы не прибавляются к `total_amount` повторно. Пока поля не классифицированы и не покрыты таким сопоставлением, статус деталей — `unverified` с причиной `ozon_api_component_mapping_incomplete`; полная отметка `reconciled` не устанавливается.

Журнал сверки хранит контрольные суммы источников и снимок API-строк. Запись net-результата выполняется атомарно только при совпадении всех групп и суммарного net-итога, завершённом импорте, отсутствии активной блокировки и открытых расхождений; она не изменяет начисления или `reconciled`. Повтор того же отчёта идемпотентен. Финансовые строки и идентификаторы из отчётов в Git не сохраняются.
