
# АвтоСклад63 — ИИ-отдел маркетплейсов

## Назначение
Единая система аналитики и контроля Ozon, Wildberries и Яндекс Маркета.

Цель: увеличение чистой прибыли АвтоСклад63 за счёт контроля продаж, рекламы, комиссий, остатков и возвратов.

## Архитектура

Главный агент маркетплейсов:
- Объединяет отчёты всех площадок.
- Рассчитывает экономику продаж.
- Выявляет убыточные товары.
- Формирует рекомендации владельцу.
- Передаёт подтверждённые потребности производства ответственным сотрудникам.

Агент Ozon:
- Поддерживает несколько кабинетов продавца.
- Получает заказы и изменения статусов.
- Анализирует продажи и возвраты.
- Учитывает комиссии, логистику и рекламу.
- Формирует черновики ответов на отзывы.

Агент Wildberries:
- Анализирует продажи, возвраты и удержания.
- Контролирует ДРР и рекламные расходы.
- Отслеживает остатки и оборачиваемость.
- Формирует рекомендации по рекламе.

Агент Яндекс Маркета:
- Анализирует заказы и продажи.
- Учитывает комиссии, логистику и другие расходы.
- Контролирует остатки и рентабельность.

## Экономика

Разделять:
- Заказы и фактические продажи.
- Выручку и выплаты маркетплейсов.
- Комиссии, логистику, хранение и рекламу.
- Себестоимость и подтверждённую чистую прибыль.

Неизвестные расходы не считать нулевыми.
Не показывать неподтверждённую прибыль как фактическую.
Сохранять источник и период каждого показателя.

## Безопасность

- Первый запуск только в режиме чтения.
- API-ключи хранить только в защищённых переменных сервера.
- `GET /api/ozon/connect` проверяет доступ владельца к Ozon Seller API чтением списка товаров.
  `OZON_CLIENT_ID` и `OZON_API_KEY` задаются только как серверные секреты Cloudflare.
  Ответ содержит `errorCode`, `stage` и `ozonHttpStatus` для диагностики, но не тело ответа Ozon.
- Не записывать секреты, персональные и финансовые данные в GitHub.
- Не менять цены, акции, ставки, заказы и остатки без согласования.
- Не выполнять автоматические списания материалов.
- Не менять существующие системы MAX и МойСклад.
- Сохранять журнал операций и ошибок.
- Исключать дублирование заказов при повторной синхронизации.

## Импорт финансов Ozon Seller API

- Код импортёра: `functions/api/ozon/finance-sync.js`.
- Внутренний Worker RPC: `workers/ozon-finance-sync.js` (`WorkerEntrypoint`). Запуск доступен только Pages Functions через Service Binding; Worker не имеет HTTP-маршрута запуска и Cron Trigger.
- Финансовые таблицы создаются миграцией `migrations/0001_ozon_finance_api_sync.sql`; защита разового тестового запуска создаётся отдельной миграцией `migrations/0002_ozon_one_shot_gate.sql`. Старые финансовые таблицы миграции не меняют.
- Импорт читает скользящее окно из трёх дат по времени `Europe/Moscow`, используя `/v1/finance/accrual/by-day` и `/v1/finance/accrual/types`. Историческая массовая загрузка не реализована.
- Контракт сверяется с [методом начислений за день](https://docs.ozon.ru/api/seller/#operation/GetFinanceAccrualByDay) и [справочником типов](https://docs.ozon.ru/api/seller/#operation/GetFinanceAccrualTypes): первая страница отправляет `date` и пустой `last_id`, следующие — тот же `date` и курсор из ответа. В `by-day` поле `item_fees` может отсутствовать или быть `null`; такие записи всё равно сохраняют каноническую сумму `total_amount`. Компоненты SKU хранятся отдельно, только если структура и денежные поля пригодны для точной атрибуции; отсутствующие суммы не заменяются нулём. `container_fees`, `non_item_fee` и `posting.delivery.services` не прибавляются к `total_amount` повторно. Метод начислений по отправлениям [описан отдельно](https://docs.ozon.ru/api/seller/#operation/GetFinanceAccrualPostings); сейчас не вызывается.
- Начисление хранится один раз по `accrual_id`; финансовый итог берётся только из `total_amount` и сохраняется целым числом копеек. Компоненты `item_fees` для SKU хранятся отдельно и не добавляются к итогу повторно.
- Страницы с `last_id` сохраняются идемпотентно. Ozon указывает срок жизни курсора 15 минут; после частичного запуска следующий запуск начинает дату заново с пустым курсором и обновляет записи по `accrual_id`. Есть пауза между вызовами, повтор HTTP 429/5xx и сетевых ошибок с учётом `Retry-After`, состояние незавершённых дат и журнал запусков. Полная пагинация не означает сверку; импортированные строки остаются несверенными.
- Финансовый экран показывает API-источник отдельно от предварительного октябрьского импорта.
- One-shot gate находится в отдельной таблице `ozon_api_one_shot_gate`; допустимы только дата `2026-10-28` и максимум две страницы. До успешного атомарного перехода `armed` → `claimed` запросов к Ozon нет. После claim повторные вызовы отклоняются, в том числе при ошибке импорта.
- Pages endpoint: `POST /api/ozon/manual-sync` и owner-only `GET /api/ozon/manual-sync`. Он проверяет Google-сессию, роль `owner`, same-origin `Origin` и JSON-запрос. Pages использует существующую офисную D1 только для проверки владельца; к тестовой D1 доступа не получает.
- Для staging Pages проекта требуется Service Binding с переменной `OZON_FINANCE_SYNC`, указывающей на Worker `autosklad63-ozon-sync-worker-test`. Сам Worker привязывается только к тестовой D1 `autosklad63-ozon-finance-sync-test` (ID `ce9dd331-929d-4c3e-9073-368de3346bc9`); `OZON_CLIENT_ID` и `OZON_API_KEY` остаются только его секретами.

### Безопасный ручной запуск (только после отдельного разрешения владельца)

1. Проверить тестовый Worker, его единственный D1 binding и наличие имён обоих секретов. Убедиться, что gate `disarmed`, записи синхронизации и начисления отсутствуют. Cron остаётся отключённым.
2. Настроить в Cloudflare Pages staging Service Binding `OZON_FINANCE_SYNC` → `autosklad63-ozon-sync-worker-test`, затем развернуть согласованную Pages версию. Не добавлять Pages binding к D1 `autosklad63-ozon-finance-sync-test`.
3. До вооружения gate проверить endpoint: owner-only POST должен получить отказ без вызова Ozon при `disarmed`; GET должен показывать `not_started`, нулевые начисления и сумму.
4. Только после отдельного разрешения владельца выполнить условный SQL `UPDATE` gate из `disarmed` в `armed` для даты `2026-10-28` и `max_pages = 2`; продолжать только при изменении одной строки.
5. Владелец выполняет один same-origin `POST /api/ozon/manual-sync` с JSON `{}`. RPC ждёт итог синхронизации: `complete`/`partial` — HTTP 200, `failed` — HTTP 502; gate отказа — HTTP 409. Тайм-аут вызова не означает успешный импорт; после него результат проверяется только через GET, повторный запуск запрещён.
6. Читать результат через owner-only `GET /api/ozon/manual-sync`. Проверить статус, число страниц/начислений, сумму в копейках, уникальные ID, ошибки и `reconciled = false`. `partial` и `failed` не считать сверкой или подтверждённой прибылью.

Эта процедура описывает будущую настройку и запуск; она не означает, что gate вооружён, Service Binding настроен или импорт выполнен.

## Первый пилот — Ozon

1. Проверить официальную документацию API.
2. Подготовить отдельное тестовое окружение.
3. Подключить основной кабинет с минимальными правами.
4. Проверить доступ и получение данных.
5. Получить заказы за согласованный период.
6. Сверить статусы, суммы и возвраты с отчётами Ozon.
7. Рассчитать экономику только по подтверждённым данным.
8. Сформировать первый отчёт в тестовом окружении.

Реальные данные получены и сверены.

Продакшен-системы не изменены.
